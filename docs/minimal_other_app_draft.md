# Minimal Other Application (Draft)

This draft explains how to stand up the smallest viable OtherLib application using the sample project at `C:/Yock/gamedev/other-testing/cmake-tests` as a reference. The goal is to build and run a driver that exercises `other_main` without additional subsystems beyond what the runtime initializes automatically. It reflects the current driver macros (`add_static_driver` / `add_dynamic_driver`) and the updated environment configuration schema living under `resources/`.

## Prerequisites

- OtherLib repository checked out and built (or installed via the CMake install step).
- CMake 3.27+ and a supported compiler (MSVC on Windows).
- External dependencies packaged by OtherLib (SDL3, Assimp, etc.) available through the install directory.

If you intend to use the installed package, confirm `C:/OtherEnvironment` (default install prefix) contains the `cmake/otherlib-config.cmake` file and the `dotnet-assemblies` folder.

## Example Project Layout

An Other Application has the following directory structure

```text
/my/project/folder/
  CMakeLists.txt
  environment.toml
  assets/
    ...
  src/
    my_project.cpp
    my_project_driver.hpp
    my_project_driver.cpp
```

Of course other configurations are possible, but this is the standard one that is generated by the Other Build Tool.

## CMake Configuration

The minimal CMake script locates the Other Environment package and links the executable against `otherlib::otherlib`. If building a static Other Environment driver, add the preprocessor definition `OTHER_APPLICATION` and link against `otherlib::otherlib_main`.

```cmake
cmake_minimum_required(VERSION 3.27)
project(OtherSample LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 23)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF) 
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

find_package(otherlib REQUIRED)

add_executable(my_project)
target_sources(my_project PRIVATE
  src/my_project.cpp
  src/my_project_driver.cpp
)

## other compilation options

target_compile_definitions(test1 PRIVATE OTHER_APPLICATION)
target_link_libraries(test1 PRIVATE otherlib::otherlib otherlib::otherlib_main)
```

### Configuring CMake

From your project directory run:

```pwsh
cmake -S . `
      -B build `
      -D CMAKE_BUILD_TYPE={Debug|Release}
```

Adjust `otherlib_DIR` if the install prefix differs.

## Other Drivers `other::driver`

The main interface for an application is the `other::driver` class in `otherlib/src/driver.{cpp|hpp}`. A minimal driver example header/source file would look like:

```cpp
/**
 * \file my_project_driver.hpp
 */
namespace my_project {

class OTHER_API my_project_driver : public other::driver {
public:
  my_project_driver(const other::config_table &config) : other::driver(config) {}
  ~my_project_driver() = default;

  void on_initialize(const command_line &cmd) override;
  void run() override;
  void on_shutdown() override;
};

} // namespace my_project

OTHER_DRIVER(my_project::my_project_driver)
```

```cpp
/**
 * \file my_project_driver.cpp
 */
#include "my_project_driver.hpp"

namespace my_project {

void my_project_driver::on_initialize(const command_line &cmd) {
  // initialize driver, parse command line args, prepare to run
}

void my_project_driver::run() {
  // main body of your application
}

void my_project_driver::on_shutdown() {
  // clean up resources, save state if needed
}

} // namespace my_project
```

## Implementing `other_main`

`otherlib` supplies the process entry point. Your code defines `other_main`, which receives the parsed command line and configuration table. A minimal implementation logs startup and exits successfully.

```cpp
other::exit_code other_main(const other::command_line& cmd, const other::config_table& config) {
  CORE_LOG_DEBUG("Hello There!");
  return other::exit_code::SUCCESS;
}
```

The simplest application to run a custom driver uses the `RUN_DRIVER` macro:

```cpp
#include "other.hpp"

other::exit_code other_main(const other::command_line& cmd, const other::config_table& config) {
  RUN_DRIVER(my_project::my_project_driver, config);
  return other::exit_code::SUCCESS;
}
```

This macro simply creates the driver, initializes, runs, and shuts the driver down, then destroys the driver and exits with `exit_code::SUCCESS`:

```cpp
other::driver* runtime = create_driver(&config);       
if (!runtime) {                                        
  CORE_LOG_ERROR("Failed to create {} driver", "my_project::my_project_driver"); 
  return other::exit_code::FAILURE;                    
}                                                      
runtime->initialize(cmd);                              
runtime->run();                                        
runtime->shutdown();                                   
destroy_driver(runtime);
```

## Optional Configuration File

An environment configuration can be provided in the form of a .toml file that can be passed in as the first command line argument

```toml
[application]
core-log-level = "info"
core-log-file = "logs/other_sample.log"

[rendering]
rendering-backend = "opengl"
window-size = { width = 1280, height = 720 }
```

Reference the file when launching:

```pwsh
cmake --build build --config Debug
./build/Debug/other_sample.exe --config config/environment.toml
```

## Verifying the Build

1. Configure and build as shown above.
2. Run the executable; confirm console output shows the OtherLib banner followed by the custom log message.
3. Check that `other_sample.log` (if configured) contains the same messages.

If the executable fails with "Multiple definition of main", confirm you removed any user-defined `main` and rely solely on `other_main`.

## Extending the Example

- Integrate rendering by enabling a backend in the config and calling into `other::subsystem<renderer_backend>::get()` once initialized.
- Load managed scripts by using the scripting environment subsystem (`other-scripting`) and placing assemblies alongside the executable.
- Package the example via `cmake --install` to verify install rules and bundled dependencies.

## Environment Configuration Reference

Common sections and keys:

- `[application]`
  - `core-log-level` / `core-log-file`: Controls logger verbosity and sink.
  - `driver`: Optional path to a dynamic driver (.dll) when the launcher loads plugins instead of a built-in executable.
- `[rendering]`
  - `rendering-backend`: Name passed to `renderer_backend::load_backend` (e.g., `opengl`).
  - `window-size`: Inline table with `width`/`height`; omit when using headless mode.
  - `force-no-window`: When true, suppresses window creation entirely, regardless of whether a rendering backend is specified or any other `[rendering]` options are set (see headless example).
- `[scripting]`
  - `dotnet-bindings`, `dotnet-runtime-config`, `other-cs-path`: Explicit bindings/runtime paths (see server config) when running outside the install layout or using custom Other Environment .NET Bindings.
  - `dotnet-modules`: Array of managed assemblies to load after the primary bindings.

When authoring a new environment file, start from the closest example above and adjust paths to match your build output. Drivers receive the parsed `config_table`, so any additional keys you add can be consumed in `other_main` via `config.get_value<T>("section.key", default)`.
